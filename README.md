## Overview

This project demonstrates an **end-to-end data engineering pipeline** for NHS-style healthcare 
claims data, built on the **Medallion Architecture** (Bronze → Silver → Gold) as implemented 
in **Microsoft Fabric**. It includes SQL migration from Oracle to Spark, a Python transformation 
pipeline, and a semantic model designed for **Power BI** reporting.

The project spans the full data engineering lifecycle: from raw source extraction, through 
SQL-level migration, to a reporting-ready semantic model with defined KPIs and Power BI measures.

## Key SQL Migration Differences

This project surfaces the most impactful Oracle → Spark SQL translation challenges:

### 1. Date Series Generation

The date dimension requires generating a sequence of calendar dates. The approaches are fundamentally different:

**Oracle (CONNECT BY LEVEL):**
```sql
SELECT TRUNC(DATE '2022-01-01') + LEVEL - 1 AS calendar_date
FROM DUAL
CONNECT BY LEVEL <= 1095;
```

**Spark SQL (SEQUENCE + EXPLODE):**
```sql
SELECT EXPLODE(
    SEQUENCE(DATE '2022-01-01', DATE '2024-12-31', INTERVAL 1 DAY)
) AS calendar_date;
```

### 2. DECODE → CASE WHEN
```sql
-- Oracle
DECODE(claim_status, 'APPROVED', 'Closed', 'REJECTED', 'Closed', 'Open')

-- Spark SQL
CASE claim_status
    WHEN 'APPROVED' THEN 'Closed'
    WHEN 'REJECTED' THEN 'Closed'
    ELSE 'Open'
END
```

### 3. Date Formatting (Case-Sensitive!)
```sql
-- Oracle — uppercase format masks
TO_CHAR(service_date, 'YYYY-MM')

-- Spark SQL — lowercase format masks (different result if wrong)
DATE_FORMAT(service_date, 'yyyy-MM')
```

### 4. LISTAGG → COLLECT_SET
```sql
-- Oracle
LISTAGG(DISTINCT procedure_code, ' | ') WITHIN GROUP (ORDER BY procedure_code)

-- Spark SQL
ARRAY_JOIN(SORT_ARRAY(COLLECT_SET(procedure_code)), ' | ')
```

## Semantic Model Summary

The semantic model is documented in `semantic_model/semantic_model_design.md`.

### Tables
| Table | Type | Grain |
|-------|------|-------|
| `fact_claims` | Fact | One row per claim |
| `dim_date` | Dimension | One row per calendar day |
| `dim_trust` | Dimension | One row per NHS Trust |
| `dim_provider` | Dimension | One row per provider |
| `dim_procedure` | Dimension | One row per procedure code |

### Key KPIs (Power BI DAX)
| KPI | Definition |
|-----|------------|
| Total Claimed (£) | `SUM(fact_claims[claimed_amount])` |
| Total Approved (£) | `SUM(fact_claims[approved_amount])` |
| Claim Approval Rate % | `DIVIDE(Approved Claims, Total Claims)` |
| Financial Approval Rate % | `DIVIDE(Total Approved, Total Claimed)` |
| Avg Submission Lag | `AVERAGE(fact_claims[submission_lag_days])` |
| Claims YTD | `CALCULATE([Total Claims], DATESYTD(...))` |
| Claims YoY Growth % | Compares to `SAMEPERIODLASTYEAR` |

## Key Learnings

**1. Medallion architecture makes the semantic layer resilient.**  
By separating raw (Bronze), cleansed (Silver), and aggregated (Gold) layers, each layer 
has a clear contract. Power BI never reads from Bronze, so ETL changes don't break reports.

**2. CONNECT BY LEVEL is a migration blocker.**  
The Oracle pattern for generating date sequences has no direct equivalent in Spark. 
Teams must know to replace it with `SEQUENCE + EXPLODE` — otherwise the entire 
date dimension query fails silently or must be rewritten from scratch.

**3. Date format case sensitivity causes silent data corruption.**  
`'YYYY'` in Spark doesn't mean year — it means the ISO week-year. The correct 
pattern is `'yyyy'`. This doesn't throw an error; it just returns wrong data. 
Aggregate validation is the only way to catch it.

**4. Direct Lake in Power BI changes the refresh conversation.**  
In traditional Power BI, data is imported and the model is a snapshot. With 
Fabric Direct Lake, the semantic model reads live Delta tables — no import step, 
near real-time data. This eliminates a whole class of refresh scheduling problems.
